# 데이트레이딩 실시간 실행 경로 설계 v1 (설계만, 주문 코드 없음)

작성 2026-10-05 · 상태: **설계 초안, 사용자 승인 전** · 대상: 탐색용 Paper 규칙 v1.0(`CONTRACT_EXPLORATORY_PAPER_DAYTRADE_V1.md`)을
소액 실계좌(USD 500~800 슬라이스)에서 그대로 돌리기 위한 장중 실행 경로.

이 문서는 실제 주문을 승인하지 않는다(Charter §4.4). 주문을 보내는 코드는 사용자 승인 전에 만들지 않는다.

## 1. 한 줄 요약

장중에는 **규칙 판단은 Paper와 같은 코드**, 시세는 Toss 웹소켓(보조로 REST), 손절은 **1차 Toss 서버 조건주문(지정가) + 2차 프로그램 감시(시장가)**,
15:55 청산과 사고 대비는 **본 프로그램과 따로 도는 감시 작업**이 맡는다. 실주문 전에 "주문 없이 실시간으로 판단만 하는 그림자 운용"으로
Paper(장 마감 뒤 계산)와 판단이 같은지 먼저 맞춘다.

## 3. 구성

```text
launchd (정규장 전 시작, 장 마감 뒤 종료)
  └─ realtime engine (한 프로세스)
       ├─ feed      : 웹소켓 trade:us(QQQ·TQQQ·SQQQ) → 로컬 1분봉, 끊김 감지
       ├─ bars      : 판단 시각에는 REST 1분봉으로 다시 맞춤(웹소켓은 LOSSY)
       ├─ decide    : src/daytrade_paper 의 상황 판단·크기 함수를 그대로 호출(규칙 정본 1곳)
       ├─ risk      : 일일 −3%, 명목 ≤ 35%, 최대 2포지션, 계좌 −35%, kill switch
       ├─ orders    : 주문 상태 기계 + 멱등 client_order_id + 저널(SQLite)
       ├─ stop L1   : 진입 체결 확인 뒤 Toss 서버 조건주문(지정가 손절)
       ├─ stop L2   : 프로그램 감시 → 조건주문 취소 후 시장가 매도
       └─ reconcile : 시작·재연결·매 분 브로커 잔고·미체결·조건주문과 대조
watchdog (별도 launchd, 15:50·15:57 ET) : 본 프로그램과 무관하게 REST로 전량 청산·확인
```

권한 순서는 기존 원칙대로 규칙(판단) → Risk → Order → Broker다. AI는 장중 판단에 들어가지 않는다(Charter §4.1).
재사용 후보: `RiskManager`(일일 한도·kill switch·청산은 한도 우회), `OrderManager`(멱등 제출), `ReconciliationService`,
`PortfolioAccount`. `BrokerProvider`에는 현재 `place_order`만 있어 취소·조회·조건주문 메서드를 더해야 한다. `TossBrokerProvider`는 빈 껍데기다.

## 4. 흐름

**시세와 봉**

- 웹소켓 체결로 1분봉을 만든다. 프레임 간격이 15초를 넘으면 `STALE`로 표시한다.
- 판단 시각(09:45, 지표일 10:15, S3 10:00, S5 14:45)에는 REST 1분봉을 받아 Paper와 같은 입력으로 판단한다.
  웹소켓 봉은 손절 감시와 표시에만 쓴다. 이렇게 하면 LOSSY 때문에 판단이 Paper와 달라지는 일을 막는다.
- 60초 PING, 끊기면 지수 백오프 재연결(최대 30초). 연결 2개 한도라 재연결 전 이전 연결을 확실히 닫는다.

**진입**

1. 규칙이 진입을 내면 Risk 검사 → 지정가 매수(매도호가 + 0.1% 이내, 시장성 지정가). 5초 안에 체결이 없으면 취소하고 그날 그 상황은 포기한다.
   시장가 대신 지정가를 쓰는 이유: 개장 직후 레버리지 ETF 호가가 벌어질 때 Paper 슬리피지(편도 0.05%)보다 크게 체결되는 것을 막는다.
2. 체결은 `personal:order`(LOSSLESS)로 확인하고 REST 주문조회로 한 번 더 맞춘다.

**손절 1차 — 서버 조건주문**

- 체결 즉시 SINGLE 조건주문: "가격 ≤ 손절가면 지정가 = 손절가 × (1 − 0.3%)로 매도". 지정가를 손절가보다 조금 낮게 두어 작은 갭에도 체결되게 한다.
- S3처럼 목표가가 있으면 OCO(목표 지정가 매도 + 손절)로 묶는다.
- OTO(매수와 손절을 한 번에)를 쓸 수 있으면 진입 직후 무방비 시간을 없앨 수 있다. 요청 형식이 확인되면 OTO를 우선한다.
- 프로그램이 죽어도 서버 손절은 남는다. 이것이 1차를 서버에 두는 이유다.

**손절 2차 — 프로그램 감시**

- 웹소켓 체결가 ≤ 손절가인데 2봉(2분) 안에 조건주문이 체결되지 않거나, 가격이 조건주문 지정가 아래로 뛰어넘었으면:
  조건주문 취소 확인 → 남은 수량 시장가 매도.
- 웹소켓이 `STALE`이고 포지션이 있으면 REST 시세를 1초마다 조회해 같은 검사를 한다(시세 15/s 한도 안).

**규칙 청산(VWAP·목표·시간)**

- 항상 "조건주문 취소 확인 → 매도" 순서다. 취소가 확인되지 않으면 매도하지 않는다(이중 매도로 공매도가 되는 것을 막는다).
  매도 수량은 브로커가 확인한 보유 수량을 넘지 않는다.

**15:55 전량 청산과 watchdog**

- 본 프로그램: 15:55에 모든 조건주문 취소 → 보유 전량 시장가 매도 → 15:57 무포지션 확인.
- watchdog(별도 launchd 작업, 15:50·15:57 ET에 해당하는 KST 쌍): 본 프로그램 상태와 무관하게 REST로 잔고를 보고,
  TQQQ/SQQQ가 남아 있으면 조건주문 취소 후 시장가 매도, 알림. 3배 ETF를 밤새 들고 가는 사고를 막는 마지막 장치다.

## 5. kill switch와 복구

- 켜지는 조건: 일일 −3%(신규 진입만 막음), 계좌 고점 대비 −35%(전량 청산·정지, 자동 재개 없음, Charter §5),
  대조 불일치, 토큰 401/403 반복, 포지션 보유 중 시세 `STALE` 60초 이상(청산), 수동 파일 플래그.
- 저널: 모든 의도·주문·체결·조건주문을 SQLite에 먼저 적고 보낸다(write-ahead). 재시작하면 브로커와 대조부터 한다.
  모르는 주문·수량이 있으면 신규 진입 없이 kill switch.
- 맥 절전·네트워크 끊김: 장중에는 `caffeinate`로 잠들지 않게 하고, 끊김 동안은 서버 손절과 watchdog가 지킨다.

## 6. 단계(각 단계는 따로 승인)

| 단계 | 내용 | 주문 | 통과 조건 |
| --- | --- | --- | --- |
| R0 | 웹소켓 장중 실측 반영(예약 시험) | 없음 | 끊김률·지연·재연결 기록. 결과로 §4 숫자(15초 STALE, 1초 REST) 확정 |

| R2 | Toss 주문 어댑터 + 극소량 시험(1주 또는 USD 5 안팎): 지정가 매수, 조건주문 생성·취소, 시장가 매도, 같은 날 재매수, watchdog 청산, 재시작 복구 | **있음(승인 필요)** | 각 경로 1회 이상 성공, 대조 불일치 0 |
| R3 | USD 500~800 슬라이스로 규칙 v1.x 운용 | **있음(승인 필요)** | 계약 §7·설계 리뷰 §5의 실계좌 단계 기준 |

R0·R1은 주문이 없어 이 설계 승인으로 시작할 수 있게 제안한다. R2부터는 주문 코드이므로 별도 승인 전에는 만들지 않는다.

## 7. 우려

- 서버 조건주문이 지정가뿐이라 큰 갭에서는 1차 손절이 안 걸린다. 2차(시장가)가 있어도 레버리지 3배라 손실이 손절폭을 넘을 수 있다.
  한도는 보장 손절가가 아니다(Charter §5). 크기 규칙(위험 0.5%/거래, 명목 ≤ 35%)이 이것을 감당하는 쪽이다.
- 소수점 주문이 레버리지 ETF에 안 되면 USD 500~800에서 정수 주식으로 명목을 맞추기 어렵다. R2 전에 확인한다.
- 이 Mac 한 대에 의존한다. 정전·절전·네트워크 문제는 서버 손절·watchdog로 피해를 줄일 뿐 없애지 못한다.
- R1에서 판단이 Paper와 다르게 나오면 실시간 실행이 Paper 결과를 재현한다고 말할 수 없다. 이때는 원인부터 고친다.

- 실시간 봉은 두 길로 얻는다. ① 웹소켓 체결을 모아 직접 만든다(빠르지만 LOSSY라 거래량이 덜 잡힐 수 있다). ② REST 1분봉을 몇 초마다 조회한다

  규칙 v1.0은 장중 거래량 급증을 신호로 쓰지 않는다. 쓰려면 새 규칙 버전과 과거 1분봉 점검이 필요하다(Charter §4.1).
