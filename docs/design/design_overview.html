AI Trading System · 설계 개요

경계만 정하면, 나머지는 자율로

사용자는 섹터/유니버스와 리스크 한도만 정한다. 그 안에서 어떤 종목을 언제 얼마나 사고팔지는 AI와 코드가 자율적으로 결정하는 다종목 자동매매 시스템. AI는 진입을 거를 수 있을 뿐, 청산·손절·생존은 언제나 코드가 책임진다.

01

핵심 원칙

이 프로젝트의 가장 큰 리스크는 AI 모델 선택이 아니라 검증되지 않은 전략과 불완전한 리스크 관리다. 따라서 모든 설계 결정은 "생존"을 수익보다 앞에 둔다.

  • 자율사용자는 경계만, 시스템이 나머지를. 섹터/유니버스·리스크 한도만 사람이 정하고 종목·타이밍·사이징은 자동.
  • 통제코드가 최종 통제권을 가진다. 생존이 수익보다 우선한다.
  • AIAI는 진입 필터 + 설명 레이어일 뿐, 절대 실행자가 아니다.
  • 청산청산·손절·서킷브레이커는 항상 AI와 독립된 순수 코드가 수행한다.
  • 리스크리스크는 종목별 + 포트폴리오 두 층에서 관리한다.
  • 순서Backtest와 Paper Trading은 반드시 Live Trading보다 앞선다. 다종목 native로 짓되 검증 유니버스는 작게.
02

자율 범위 — 사람과 기계의 분담

"큰 개입 없이 자동으로." 사람이 내리는 결정은 경계와 안전장치에 한정되고, 나머지 판단은 시스템이 자율적으로 수행한다. SOXL은 대표 단타 종목일 뿐 범위가 아니다.

사람이 정하는 것

  • 섹터 / 유니버스 경계
  • 리스크 한도 (노출·손실·포지션 수)
  • on / off · Kill Switch

시스템이 자동으로 하는 것

  • 종목 선별 (Universe Screener)
  • 진입 판단 (Rule + AI filter)
  • 포지션 사이징 · 타이밍 · 청산
03

교차 서비스 & 규칙

  • 선별UniverseScreener — 섹터/유니버스에서 tradable 후보를 자율 선별. 종목 선택은 여기서만.
  • 포트폴리오Portfolio Risk — 동시 포지션 수·전체 노출·섹터 집중도·드로다운을 종목별 리스크 위에서 관리.
  • 정합성ReconciliationService — 전 종목 내부 position DB와 브로커 실잔고를 대조. 진실의 원천은 브로커.
  • 지표IndicatorEngine — 백테스트·실거래·스크리너가 100% 동일 모듈 공유 (train/live skew 차단).
  • 경계Provider는 데이터 fetch와 주문 실행만. 선별·판단·지표·리스크 로직은 Provider 밖.
04

AI의 권한 경계

"코드가 최종 통제"의 정확한 정의. AI는 신규 진입에 대해서만 제한적 veto를 갖는다.

AI가 막을 수 있음

  • 신규 매수 진입
  • 추가 매수 · 물타기
  • confidence 미달 시 BUY 차단

AI가 할 수 없음

  • 후보 없는 BUY 강제
  • 손절 · 청산 차단
  • 일일 손실 한도 · 킬 스위치 무시
iAI 실패(timeout / error / rate limit / invalid JSON / low confidence)는 시스템 장애가 아니라 매매 금지 조건으로 처리 → 해당 사이클 WAIT. 단, 청산 경로에는 절대 적용하지 않는다.

리스크 관리 — 종목별 + 포트폴리오

다종목이므로 리스크를 두 층에서 본다. 레버리지 상품은 종목별 leverage_factor로 실질 노출을 계산한다. effective_exposure = notional × leverage_factor

종목별 사이징 (실질 노출)

  • 초기 1회 진입: 계좌 명목 3~5%
  • 단일 종목 실질 노출: 15~30%
  • 종목별 leverage_factor 적용 (SOXL=3)

포트폴리오 한도

  • 동시 포지션 수 상한 N
  • 전체 실질 노출 합계: ≤ 50%
  • 섹터 집중도 · 상관관계 한도

오버나잇 & 연장시간 (레버리지 차등)

  • 일반주(×1): 오버나잇 보유 허용
  • 레버리지 ETF(>1): 세션 마감 전 청산
  • 프리/애프터: 지정가 우선 + 유동성 게이트
i킬 스위치 발동 후 자동 재개 금지. postmortem(원인·주문로그·포지션·API 상태) 검토 후 운영자 수동 승인으로만 재개.
06

MVP 범위

다종목 native로 설계하되, 첫 Live 검증 유니버스는 작게. SOXL은 대표 검증 종목이자 레버리지 ETF 케이스일 뿐 범위 제한이 아니다.

단일 계좌 다종목 · Screener 자율 선별 검증 유니버스 작게 (3~5) 동시 포지션 상한 N 5분봉 의사결정 프리+정규+애프터 오버나잇 레버리지 차등 종목별 분할매수 2~3회 숏 · 헤징 미지원

08

검증 전제 — Feasibility Blockers

코드 작성 전 반드시 통과해야 하는 실증 항목. 하나라도 실패하면 설계가 아무리 좋아도 프로젝트가 성립하지 않는다.

BLOCKER 1주문

Toss 미국주식 자동주문 API

프로그래매틱 주문·잔고·체결 조회가 실제로 가능한가? 주문 유형, 소수점, USD 환전, rate limit, 샌드박스 여부.

불가 시 MVP Broker를 KIS로 교체
BLOCKER 2데이터

유니버스 과거 분봉 데이터

섹터 종목군의 1~3년 1/5분봉을 어디서 확보? 다종목 대량 조회 제한·비용, split-adjusted 여부. 없으면 백테스트·스크리너 불가 → Live 불가.

KIS 해외주식분봉 또는 Polygon
BLOCKER 3참조

참조지표 & 다종목 실시간 시세

여러 종목 동시 실시간 시세(동시 구독 수) + 섹터 벤치마크(SOXX/SMH/QQQ) + VIX. 실거래·백테스트 소스의 봉 집계·타임스탬프 정합성.

VIX 미지원 시 Polygon 도입 확정
